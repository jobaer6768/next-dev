# Assignment 4 — Build a SaaS Backend

> **Mission 4 · Part A · Capstone Backend**
> Capstone of the multi-tenant SaaS series. You ship a production-shaped, multi-tenant API.

---

## 1. Project Brief

You are the **backend lead** at a small SaaS startup. Your product is a **multi-tenant project-management SaaS** — the same product the team has been building across Missions 1, 2, and 3. By the end of Mission 3 you have a CLI tool, a data pipeline, and integration tests for it. Mission 4 turns that backend-of-your-CLI into a real, deployed, multi-tenant HTTP service that other engineers (and, in Assignment 5, a frontend) can call.

In the prior modules (18–27) you learned Drizzle ORM, schema relations, multi-tenant design, project bootstrap, Zod validation, JWT auth, RBAC, workspaces & teams, file management, search/filter/pagination, and production patterns. **This assignment is where you put it all together into one cohesive service.**

You will design and ship:

- A **layered Express + TypeScript service** (route → controller → service → repository).
- A **shared-schema, workspace-scoped** multi-tenant database on PostgreSQL 16.
- **JWT auth with RBAC** at three roles (owner / admin / member).
- **Workspace lifecycle** (create, switch, invite via single-use token, accept, revoke).
- **File management** backed by S3 or Cloudinary with signed URLs and per-workspace quota.
- **Search, filter, and cursor-based pagination** on every list endpoint.
- **Analytics endpoints** (workspace stats, time-series, top contributors).
- **Drizzle migrations** checked into the repo, no `db:push` in production.
- **OpenAPI documentation** generated from Zod (or a hand-written `docs/API.md`).
- A **deployed link** OR a `docker compose up` that brings the whole system online locally.

The product domain is flexible — you may build a project-management tool, a helpdesk, a CRM, or a ticketing system. **Pick one and commit to it.** The grading rubric does not care which you pick, but you will be marked down for a half-built feature set.

> **Senior-engineer note:** A real backend is judged on what happens at 03:00 when something breaks — not on the happy path. Half of the marks in this assignment are for production patterns: structured errors, logs, validation, migrations, and tests. Don't just make it work; make it survive.

## 3. Conceptual Sessions (3 × ~90 min)

These three sessions build **one** medium backend project end-to-end. They are not three separate projects; the second session continues the first, and the third ships it.

### Session 1 — "Schema & setup: requirements, ERD, and Drizzle schema for a small multi-tenant app"

**Module references:** 18 (Drizzle ORM), 19 (Drizzle relations), 20 (multi-tenant design), 21 (project bootstrap & validation).

**You will:**

1. Pick your domain. Write a one-paragraph product brief: name, who it serves, the 3–5 features you will ship. Save it to `BRIEF.md`.
2. Draw an ERD (Mermaid, dbdiagram.io, or hand-drawn + photo) covering: users, workspaces, members, projects, tasks, comments, attachments, invitations.
3. Bootstrap the project: `pnpm init`, TypeScript strict, ESLint, Prettier, Pino logger, Zod, Drizzle, Express, dotenv, vitest.
4. Write the Drizzle schema. Use a **shared schema with `workspace_id` on every tenant-owned table** (this is the assignment's default pattern; explain in the README why you did not choose schema-per-tenant).
5. Generate the first migration with `drizzle-kit generate`. Review the SQL. Do not edit it by hand.
6. Wire `db/client.ts`, `db/seed.ts`, and a `/health` route that pings the DB.

**Exit criteria:** `pnpm dev` starts the server, `GET /health` returns `{ ok: true, db: 'up' }`, and `pnpm db:seed` populates the demo data.

**Outcomes:** Module 18 (table definitions, enums), Module 19 (one-to-many and many-to-many relations, especially `users ↔ workspaces` via `members`), Module 20 (the `workspace_id` column on every tenant table and the helper `scopeToWorkspace(query, workspaceId)`).

### Session 2 — "Auth & tenancy: JWT auth, RBAC, and workspace-scoped queries"

**Module references:** 22 (JWT auth), 23 (RBAC), 24 (workspaces & teams), 25 (data & file management — the auth gate for it).

**You will:**

1. Implement `/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout`. Hash with bcrypt (cost 12). Issue short-lived access JWTs (15 min) and long-lived refresh tokens (7 days, stored hashed in `refresh_tokens`).
2. Build the `requireAuth` middleware. Decode the JWT, load the user, attach `req.user`.
3. Build the `requireRole(...roles)` middleware that compares against `req.workspaceRole`.
4. Implement workspace routes: `POST /workspaces` (creator becomes owner), `GET /workspaces` (mine), `GET /workspaces/:id` (member-only), `PATCH /workspaces/:id` (admin+), `DELETE /workspaces/:id` (owner only).
5. Implement member routes: `GET /workspaces/:id/members`, `PATCH /members/:id` (admin+, demote/ promote), `DELETE /members/:id` (admin+, cannot remove last owner).
6. Implement invitations: `POST /workspaces/:id/invitations` (admin+), `GET /invitations/:token` (public, shows workspace name only), `POST /invitations/:token/accept` (authenticated), `DELETE /invitations/:id` (admin+ revoke).
7. Make every repository function take `workspaceId` as the first argument. **No raw `db.select()` outside `/repositories`.**

**Exit criteria:** A full auth + workspace flow works in Postman: register → create workspace → invite a second user → second user accepts → admin demotes owner (fails) → owner promotes admin → owner deletes the workspace (succeeds, cascade).

**Outcomes:** Modules 22–24 in their entirety, plus the start of Module 25 (the `attachable` pattern that files will plug into in Session 3).

### Session 3 — "Features & finish: CRUD, search/filter/pagination, error handling, API docs"

**Module references:** 25 (data & file management), 26 (search/filter/pagination), 27 (production backend).

**You will:**

1. Build the domain CRUD: `projects` and `tasks` (or whatever your domain's core entities are). Validation with Zod on every body, query, and params. 400 with a `details` array on bad input.
2. Wire **search, filter, and pagination on every list endpoint**:
   - `?q=…` for full-text-ish search (use `ILIKE` for now, mention `pg_trgm` in README).
   - `?status=open&assignee=…&tag=bug` for filters.
   - `?cursor=…&limit=20` for **cursor-based pagination** on `tasks` (keyset on `created_at, id`). Offset is acceptable on small tables.
3. Add file management: `POST /workspaces/:id/files` (multipart, Multer), upload to S3/Cloudinary, store the key + mime + size + uploader in `files`. `GET /files/:id/url` returns a **signed URL** with 5-minute TTL. Enforce **per-workspace quota** (e.g. 100 MB) and reject uploads that would exceed it with `413 Payload Too Large`.
4. Add analytics:
   - `GET /workspaces/:id/analytics/overview` → counts (projects, tasks, members, storage).
   - `GET /workspaces/:id/analytics/timeseries?metric=tasks_created&from=…&to=…&bucket=day` → `[{ bucket, value }]`.
   - `GET /workspaces/:id/analytics/top-contributors?metric=tasks_completed&limit=10` → `[{ userId, name, count }]`.
5. Centralize errors: a single `errorHandler` middleware that maps your `AppError` subclasses to HTTP status codes and a consistent JSON shape `{ error: { code, message, details? } }`.
6. Generate OpenAPI: use `zod-to-openapi` (or `@asteasolutions/zod-to-openapi`) to derive a spec from your Zod schemas. Serve it at `/docs`.
7. Write tests: unit tests for at least two services (e.g. `WorkspaceService`, `TaskService`), integration tests for `/auth`, `/workspaces`, and `/tasks`, one E2E test that runs the full invite flow.
8. Write `README.md` and `docker-compose.yml`. Run `docker compose up`, hit the API, take screenshots.

**Exit criteria:** `docker compose up && bash scripts/verify.sh` exits 0. Swagger UI is reachable at `/docs`. README walks a new engineer from zero to a working request in under 5 minutes.

**Outcomes:** Modules 25, 26, 27 in full. This is your portfolio piece.

## 7. AI Industry Note — "Why Multi-Tenancy Is the Hard Part"

Multi-tenant SaaS is the most over-asked-about and under-explained interview topic in backend engineering. Here is what production teams actually care about.

**The three tenancy models are not equal.** Schema-per-tenant is the most isolated and the most operationally expensive: every tenant is a migration, a connection pool, and a backup target. Schema-per-tenant is appropriate for a small number of high-touch enterprise customers, not for self-serve SaaS. Schema-per-database is the most expensive of all — only justifiable for regulated workloads (HIPAA, FedRAMP). For 99% of SaaS products, **shared schema with a `tenant_id` column** is the right answer, and the rest of this note assumes it.

**The bug that ships to production most often is "missing `tenant_id` in the WHERE clause".** It is not a typo; it is a missing line of thought. Defense in depth: (1) every repository function takes `workspaceId` as the first parameter and never reads it from the query body; (2) every tenant-scoped table has a composite index `(workspace_id, …)` so a query without `workspace_id` is full-scan-detectable in `EXPLAIN`; (3) tests assert that user A cannot read user B's row, even with the row's real ID.

**Cursor pagination is non-negotiable on real data.** `OFFSET 100000` is `O(n)` on the database. On a 10M-row `tasks` table it will eventually take seconds and lock the table. Keyset pagination (`WHERE (created_at, id) < ($cursor_ts, $cursor_id) ORDER BY created_at DESC, id DESC LIMIT 20`) is `O(log n)`. The cost is that the cursor is opaque and you cannot "jump to page 50" — but no real user wants page 50 of 10M rows; they want a filter.

**Signed URLs are the smallest change with the biggest security win.** If your API proxies file bytes, you are paying bandwidth twice and becoming a target for hot-linking. Generate a short-lived signed URL on S3/Cloudinary and redirect. Five minutes is the typical TTL; longer is a leak waiting to happen.

**Finally: this is the assignment where you learn what "production patterns" means.** Not Helmet, not rate limiting, not Docker. Those are table stakes. Production patterns mean: *the system fails loudly, recovers automatically, and tells you what happened.* Structured logs with correlation IDs, a `/health` route that does not depend on the DB, a `/ready` route that does, graceful shutdown that drains in-flight requests, and an error catalog that the on-call engineer can search. The next assignment (5) builds a UI on top of this — and you will be grateful for every error code you documented when the frontend asks "what does 409 mean here?"
